fix(yt): 127.0.0.1 콜백 실패 2가지 원인 진단 및 해결

## 증상
로이 PC 에서 youtube_auth.cmd 실행 시 브라우저가 계속
ERR_CONNECTION_REFUSED / "127.0.0.1 에서 안 된다"고 보고.

## 진단 (scripts/diag_localhost.py 신설로 실측)
1) **localhost 가 IPv6(::1) 이 먼저 해석됨**
   - 이 PC 에선 ::1 이 127.0.0.1 보다 먼저 나온다.
   - 브라우저도 ::1 을 먼저 시도 → IPv4 전용 서버면 '거부됨' 이 된다.
2) **프록시 환경변수가 콜백을 빼앗아감**
   - HTTP_PROXY=http://127.0.0.1:6222 가 설정돼 있음
   - 이 상태면 Google 이 127.0.0.1 로 보내는 **콜백까지 프록시로 빠져나간다.**

## 근본 원인: 직접 만든 서버가 Google 공식 구현과 달랐음
직접 wsgiref 서버를 만들었더니 두 가지가 틀렸다:
- `flow.credentials` 는 속성이 아니라 내부 상태다. getattr 로 판정하면 항상 실패.
- 콜백을 받는 정확한 방식(wsgi_app.last_request_uri → fetch_token)을
  재현하지 못했다.

## 해결
**Google 공식 구현을 그대로 사용** — 직접 만들지 않는다:
```python
creds = flow.run_local_server(
    host="localhost", port=0, open_browser=False,
    timeout_seconds=..., authorization_prompt_message="...")
```
- host="localhost" → IPv6/IPv4 모두 처리
- open_browser=False → URL 만 stdout 에 출력 (로이가 붙여넣기)
- 내부적으로 콜백 수신 + fetch_token 을 모두 처리해 신뢰성 보장

추가로 프록시 변수를 코드와 배치 양쪽에서 제거.

## 변경
1. scripts/diag_localhost.py — IPv4/IPv6/프록시 진단 도구 (재발 방지)
2. scripts/youtube_auth.py — Google 공식 run_local_server 사용으로 교체,
   프록시 무력화, 미사용 코드 제거 (직접 만든 서버/time import 등)
3. scripts/youtube_auth.cmd — 프록시 변수 제거 + 거부 에러 상세 안내

## 참고
이전 방식은 sandbox 검증용이었다. 로이 PC 에서는 공식 구현을 쓰는 것이
확실히 안전하다. (직접 만든 WSGI 서버는 콜백 처리 누락 위험)
